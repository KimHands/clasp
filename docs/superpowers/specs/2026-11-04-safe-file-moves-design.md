# 파일 이동 안전 설계

개편 범위 B의 첫 번째 묶음이다. 나머지 묶음(전송 경계, 분류 품질, 빌드와 CI, 읽기 전용 MCP)은 별도 문서로 다룬다.

## 목표

Clasp의 정리와 되돌리기가 사용자 파일을 덮어쓰거나, 다른 파일을 옮기거나, 기록과 실제 파일을 어긋난 채로 두지 않는다. 이 성질을 테스트로 고정한다.

### 보장 범위

- 보장한다: Clasp 자체의 모든 실행 경로, 프로세스 중단, DB 커밋 실패, 실행 사이에 사용자가 파일을 바꾼 경우.
- 보장하지 않는다: 같은 사용자 권한의 다른 프로세스가 이동 호출 사이의 극히 짧은 틈에 같은 경로를 바꾸는 경우. POSIX에서 링크 생성과 원본 삭제는 별도 호출이라 이 틈을 없앨 수 없다. 틈을 줄이고 가능한 곳에서 탐지하며, 잔여 위험으로 명시한다.
- 파일시스템이 하드링크를 지원하지 않으면(macOS의 exFAT 외장 디스크 등) 이동을 실패로 기록하고 파일은 그대로 둔다.

## 현재 문제

임시 폴더에서 실제 코드를 실행해 재현했다.

| 시나리오 | 현재 결과 |
|---|---|
| 덮어쓰기, 대상 파일이 이미 스캔됨 | 기존 파일이 사라지고 `/apply`가 500을 반환한다. 이동 로그가 남지 않아 Undo도 불가능하다 |
| 덮어쓰기, 대상 파일이 스캔 후 생김 | 기존 파일이 사라지고 Undo로 복구되지 않는다 |
| 정리 후 원위치에 새 파일 생성, 이후 Undo | 새 파일을 확인 없이 덮어쓴다 |
| 이동한 파일 일부를 지운 뒤 Undo | 1건이 실패해도 이력은 되돌림 완료로 표시된다 |
| 파일이 하위 폴더에만 있을 때 정리 | 스캔 루트가 아니라 공통 하위 폴더 안에 정리된다 |
| 배치 A 후 파일을 배치 B로 다시 옮기고, 다른 파일을 같은 경로로 옮긴 뒤 A를 Undo | 다른 파일을 원위치로 옮기고 성공으로 보고한다 |
| 파일 심볼릭 링크 스캔 | 링크를 따라 스캔 루트 밖 파일의 본문을 읽는다 |
| 상대 심볼릭 링크 이동 | 이동 후 링크가 깨진다 |

코드를 읽어 확인한 위험도 있다.

- 존재 확인과 이동 사이에 대상 파일이 생기면 덮어쓴다(`shutil.move`).
- 스캔 루트 안의 폴더가 바깥을 가리키는 심볼릭 링크면 파일이 루트 밖으로 나갈 수 있다.
- 경로 범위 검사가 `startswith`라 `/a/b`와 `/a/bc`를 구분하지 못한다.
- 이동 도중 프로세스가 죽으면 무엇이 움직였는지 기록이 없다.

## 결정

### 덮어쓰기 제거

충돌 처리는 `rename`과 `skip`만 남긴다.

- `POST /apply`는 `overwrite`를 `INVALID_TYPE`(400)으로 거부한다.
- Apply 화면의 선택지에서 뺀다.
- 과거 이력을 표시할 수 있도록 `RESOLUTION_LABELS`의 `overwrite` 라벨은 유지한다.

### 심볼릭 링크는 다루지 않는다

- 스캔의 `_collect_files`는 파일 심볼릭 링크를 수집하지 않는다.
- 정리는 경로가 심볼릭 링크인 파일을 `skip`으로 기록하고 옮기지 않는다. 이전 스캔이 남긴 행에 대비한 것이다.

### 이동 원자 연산

`services/safe_move.py`에 `move_no_clobber(src, dst)`를 둔다. 대상이 이미 있으면 `FileExistsError`를 내고 아무것도 바꾸지 않는다.

- **Windows:** `os.rename(src, dst)`. 대상이 있으면 실패하고, 호출 하나로 끝난다.
- **그 외:** `os.link(src, dst, follow_symlinks=False)` 후, 두 경로의 `lstat`이 같은 파일일 때만 `os.unlink(src)`한다. 다르면 원본이 바뀐 것이므로 원본을 지우지 않고 `ConcurrentChange`(`OSError` 하위 클래스)를 낸다.
- **원본 삭제 실패:** 대상 경로가 여전히 원본과 같은 파일일 때만 대상을 지우고 예외를 다시 던진다. 경로 이름만으로 지우지 않는다.
- **하드링크 미지원과 볼륨 간 이동:** 대체 경로를 두지 않고 `OSError`를 그대로 전파한다. `O_EXCL`로 자리를 잡은 뒤 `os.replace`하는 방식은 자리가 바뀌면 다른 파일을 덮어쓸 수 있고, 복구 때 빈 사용자 파일과 구분할 수 없다.

`shutil.move`는 이동 코드에서 쓰지 않는다.

### 파일 식별값

경로만으로는 그 자리의 파일이 Clasp이 옮긴 파일인지 알 수 없다. 이동 전 원본의 `st_ino`를 기록해 복구와 되돌리기에서 비교한다. 하드링크와 같은 볼륨 내 이름 변경은 `st_ino`를 유지한다.

- 새 테이블 `action_log_identities`(`log_id` PK·FK, `inode` 문자열)에 저장한다. Windows의 값은 SQLite 정수 범위를 넘을 수 있어 문자열로 둔다.
- 기존 테이블은 바꾸지 않는다. `create_all`이 새 테이블만 만들므로 사용자 DB 마이그레이션이 필요 없다.
- 사용자가 파일을 제자리에서 수정하면 `st_ino`가 유지되어 되돌릴 수 있다. 원자적 저장을 쓰는 편집기로 수정하면 값이 바뀌어 `identity_mismatch`로 보고되고, 파일은 그대로 남는다. 잘못 옮기는 것보다 옮기지 않는 쪽을 택한다.
- 식별값이 없는 과거 로그는 비교를 건너뛴다. 덮어쓰지 않는 보장은 그대로 적용된다.

### 스캔 후 바뀐 파일

스캔 뒤 같은 경로의 파일이 바뀌었다면, 그 분류를 다른 파일에 적용하게 된다. 정리 직전에 `lstat`의 크기와 수정 시각을 `File.size`, `File.modified_at`과 비교해 다르면 `skip`으로 기록하고 옮기지 않는다. 재스캔하면 다시 정리할 수 있다. 값이 없는 행은 비교를 건너뛴다.

### 이동 전 기록

파일 하나의 처리 순서는 다음과 같다.

1. 원본 `st_ino`와 함께 `action_type="pending"` 로그를 커밋한다.
2. 대상 폴더를 만들고 `move_no_clobber`를 실행한다.
3. 로그를 `move`로 바꾸고 `File.path`를 함께 커밋한다.
4. 2에서 예외가 나면 로그를 `failed`로 기록하고 다음 파일로 넘어간다. 대상이 그 사이 생겼어도 재시도하지 않는다. 파일은 제자리에 남고 실패로 보고된다.
5. 3에서 예외가 나면 파일은 이미 옮겨졌으므로 롤백하고 로그를 `pending`으로 남긴 채 실패로 집계한다. 조정 절차가 확정한다.

파일 하나의 실패로 요청 전체가 500이 되지 않는다.

### 조정 절차

`services/move_recovery.py`의 `reconcile_pending(db)`가 남은 `pending`과 `undo_pending` 로그를 실제 파일과 대조한다. **앱 시작 시뿐 아니라 스캔, 정리, 되돌리기를 시작할 때도 실행한다.** 재시작 전에 재스캔이나 재정리가 일어나도 기록이 어긋나지 않게 하기 위해서다.

판정은 `lstat`의 `st_ino`로 한다. `os.path.samefile`은 쓰지 않는다. "일치"는 기록된 식별값과 같다는 뜻이다.

`pending`(원본 → 대상):

| 대상 | 원본 | 판단 | 처리 |
|---|---|---|---|
| 일치 | 없음 | 이동 완료 | `move`로 확정, `File.path` 갱신 |
| 일치 | 같은 파일 | 링크 직후 중단 | 대상 링크만 지우고 `failed` |
| 일치 | 다른 파일 | 링크 후 원본이 바뀜 | `move`로 확정. 원본 자리의 파일은 건드리지 않는다 |
| 없음 | 무관 | 이동 안 됨 | 파일을 건드리지 않고 `failed` |
| 불일치 | 있음 | 이동 안 됨 | 파일을 건드리지 않고 `failed` |
| 불일치 | 없음 | 판단 불가. 이동 뒤 사용자가 파일을 교체했을 수 있다 | 파일을 건드리지 않고 `unverified`. 실패로 집계하고 되돌리기 대상에서 뺀다 |

`undo_pending`(대상 → 원본):

| 원본 위치 | 대상 위치 | 판단 | 처리 |
|---|---|---|---|
| 일치 | 없음 | 되돌리기 완료 | `move`, `is_undone=True`, `File.path` 갱신 |
| 일치 | 같은 파일 | 링크 직후 중단 | 원본 위치 링크만 지우고 `move`로 복귀 |
| 일치 | 다른 파일 | 링크 후 대상이 바뀜 | `move`, `is_undone=True`, `File.path` 갱신. 대상 자리의 파일은 건드리지 않는다 |
| 없음 또는 불일치 | 무관 | 되돌리기 안 됨으로 처리 | 파일을 건드리지 않고 `move`로 복귀. 파일이 이미 돌아온 뒤 교체된 경우라면 재시도가 `destination_file_not_found`로 보고한다 |

- **미해결이 남으면 막는다:** `reconcile_pending`은 처리하지 못한 로그 수를 돌려준다. 0이 아니면 정리와 되돌리기는 `MOVES_UNRESOLVED`(409)로 거부하고, 스캔은 오류 단계로 끝낸다. 해결되지 않은 이동 위에 새 행과 새 이동이 쌓이면 나중에 조정할 수 없기 때문이다. 앱 시작은 막지 않는다.
- **행을 지우지 않는다:** `File.path`를 갱신할 때 그 경로를 다른 행이 쓰고 있으면 갱신을 건너뛰고 경고를 남긴다. 미해결 중에는 스캔이 막히고 정리는 점유된 경로를 고르지 않으므로 정상 경로로는 생기지 않는다. 삭제하면 수동 분류를 잃을 수 있다.
- 조정이 끝난 배치는 `moved_count`와 `failed_count`를 로그 기준으로 다시 계산한다. `unverified`는 실패로 센다.
- 로그마다 따로 커밋하고, 하나의 실패가 나머지 로그의 처리를 막지 않는다.
- 식별값이 없는 `pending`은 없다. 이 절차가 생긴 뒤에만 `pending`이 만들어지기 때문이다.

### 대상 경로 점유 판단

`_resolve_conflict`는 디스크 존재 여부(`lexists`)에 더해 다른 `File` 행이 그 경로를 쓰고 있는지도 본다. 디스크에 파일이 없어도 오래된 행이 경로를 잡고 있으면 `files.path` 유니크 제약에 걸리기 때문이다. 점유된 경로는 `rename`이면 번호를 붙이고 `skip`이면 건너뛴다. 미리보기의 충돌 판단도 같은 함수를 쓴다.

### 정리 기준 폴더

`_find_common_base` 추측을 없애고 요청의 `folder_path`를 기준으로 삼는다.

- `/apply/preview`에도 `folder_path`를 필수로 받는다. 미리보기와 실제 이동의 기준을 같게 하기 위해서다.
- `realpath`로 정규화한 뒤 스캔과 같은 허용 범위(홈 아래) 검사를 적용한다. `_validate_folder_path`를 라우터에서 공용 위치로 옮긴다.
- 모든 대상 파일이 기준 폴더 안에 있어야 한다. 하나라도 벗어나면 이동 전에 요청 전체를 `PERMISSION_DENIED`로 거부한다.
- 범위 검사는 `os.path.commonpath`로 하고, 비교 전에 NFC로 정규화한다.
- 대상 디렉터리의 `realpath`를 만들기 전에 확인한다. 심볼릭 링크로 기준 폴더를 벗어나면 그 파일을 `failed`로 기록하고 바깥에 아무것도 만들지 않는다.

### 되돌리기

배치의 `move` 로그마다 다음 순서로 판단한다.

| 조건 | 사유 | 처리 |
|---|---|---|
| 대상 위치에 파일 없음 | `destination_file_not_found` | 건너뜀 |
| 식별값 불일치 | `identity_mismatch` | 건너뜀 |
| 원위치 폴더의 `realpath`가 배치의 기준 폴더 밖 | `source_outside_root` | 폴더를 만들지 않고 건너뜀 |
| 원위치 점유(파일 또는 다른 `File` 행) | `source_occupied` | 건너뜀 |
| 이동 또는 커밋 실패 | `move_failed` | 조정 절차가 정리 |

- 이동 전에 로그를 `undo_pending`으로 커밋하고, `move_no_clobber` 직후 `File.path`와 `is_undone`을 한 번에 커밋한다. 커밋이 실패하면 다음 조정이 완료로 확정한다.
- `ActionBatch.is_undone`은 모든 `move` 로그가 되돌려졌을 때만 참이 된다.
- 실패한 항목은 같은 `action_log_id`로 다시 시도할 수 있다.

### 이력 상태

`GET /apply/history` 응답에 로그에서 계산한 `undo_state`를 더한다.

| 값 | 조건 |
|---|---|
| `none` | 되돌린 로그가 없다 |
| `partial` | 일부만 되돌렸다 |
| `undone` | 모두 되돌렸다 |

기존 `is_undone` 필드는 유지한다. 조회는 요청 경로와 `realpath` 두 값으로 찾아 과거 이력도 나오게 한다.

### 프런트엔드

- Apply 화면은 `undo_state`로 표시하고, `partial`이면 "일부 되돌림"과 다시 시도 버튼을 보여 준다.
- `applyStore`는 Undo 후 무조건 `is_undone: true`로 바꾸지 않고 이력을 다시 불러온다.
- 어느 배치를 되돌리든 결과 카드를 표시한다. 모든 항목이 실패하면 `undo_state`가 `none`으로 남아 이력만으로는 실패를 알 수 없기 때문이다.
- `failed > 0`이면 제목을 "일부만 되돌렸습니다"로 하고, 사유는 사용자 문구로 표시한다.
- 미리보기 호출에 `folderPath`를 넘긴다.

### DB 스키마

기존 테이블은 바꾸지 않고 `action_log_identities` 테이블 하나만 추가한다. `action_type`에는 `pending`, `undo_pending`, `unverified` 값이 늘어나지만 자유 문자열 컬럼이다. `undo_state`는 저장하지 않고 계산한다.

## 범위 밖

- 재스캔 시 수동 분류와 규칙이 화면에 반영되지 않는 문제: 분류 품질 묶음에서 다룬다.
- 서비스 함수의 비동기 전환: 이동이 오래 걸리면 이벤트 루프를 막는 문제는 남는다. 손실과 무관하므로 빌드와 CI 묶음 이후에 판단한다.
- 볼륨 간 이동과 하드링크 미지원 파일시스템 지원.
- Windows 동작 검증: 이 묶음의 테스트는 macOS에서 실행한다. Windows 분기는 빌드와 CI 묶음의 Windows 실행으로 검증하며, 그 전까지 미검증으로 표기한다.

## 테스트

`backend/tests/`에 pytest를 추가한다. 실제 파일을 임시 폴더에서 옮기고, DB는 테스트마다 임시 SQLite를 쓴다. 임베딩 모델은 불러오지 않는다. 고치기 전에 각 테스트가 실패하는 것을 먼저 확인한다.

- `move_no_clobber`: 정상 이동, 대상 존재 시 양쪽 파일 불변, 하드링크 불가 시 원본 유지, 링크 후 원본 교체 시 새 원본 유지, 원본 삭제 실패 시 원본 유지, 정리 전 대상 교체 시 새 대상 유지.
- 스캔: 파일 심볼릭 링크 미수집.
- 정리: 대상 점유 시 `rename`과 `skip`, 오래된 `File` 행이 점유한 경로, `overwrite` 거부, 낮은 신뢰도 파일 제외, 심볼릭 링크 파일 `skip`, 스캔 후 바뀐 파일 `skip`, 기준 폴더 이탈 거부, 심볼릭 링크 폴더 이탈 `failed`, 파일 하나의 실패 후 나머지 진행.
- 되돌리기: 원위치 점유 시 `source_occupied`, 다른 파일이 같은 경로에 있을 때 `identity_mismatch`, 원위치 폴더가 기준 폴더 밖을 가리킬 때 `source_outside_root`, 일부 실패 시 `partial`, 재시도 후 `undone`, 과거 배치 시나리오.
- 조정: 위 두 판정 표의 모든 행, 미해결 시 정리·되돌리기·스캔 거부, 경로를 쓰는 다른 행이 있어도 행을 지우지 않음, 재시작 없이 정리·되돌리기·스캔을 시작할 때 실행.
- 불변식: 위 시나리오를 실행한 뒤 시작 시점 모든 파일의 해시가 어딘가에 그대로 남아 있다.
- 프런트엔드: 앱을 실행해 충돌 모달에 덮어쓰기가 없고, 과거 배치의 되돌리기 실패 사유와 일부 되돌림이 표시되는지 확인한다.

## 완료 기준

- 위 테스트가 모두 통과한다.
- "현재 문제" 표의 재현 시나리오를 실제 코드로 다시 돌렸을 때 파일 손실과 잘못된 이동이 없다.
- `docs/API_명세서.md`의 `conflict_resolution`, 미리보기 파라미터, 이력 응답, 되돌리기 사유를 코드와 맞춘다.

## 다른 벤더 리뷰 반영

Codex(1회차) 지적을 재현이 가능한 것은 직접 측정한 뒤 판정했다.

| 지적 | 판정 | 근거·조치 |
|---|---|---|
| `O_EXCL` 후 `os.replace`가 다른 파일을 덮어쓸 수 있다 | 수용 | 공식 동작. 대체 경로 삭제 |
| 크기 0 파일을 예약 파일로 오인해 지운다 | 수용 | 대체 경로 삭제로 판정 자체를 없앰 |
| 링크 후 원본이 바뀌면 새 원본을 지운다 | 부분 수용 | `lstat` 비교로 탐지. 잔여 틈은 POSIX 한계로 보장 범위에 명시 |
| 실패 정리가 다른 파일을 지운다 | 수용 | 같은 파일일 때만 지움 |
| 원본 없음·대상 있음만으로 완료 확정 | 수용 | `st_ino` 기록과 비교 |
| Undo 커밋 실패가 복구되지 않는다 | 수용 | `undo_pending`과 조정 절차 |
| 커밋 실패 후 재스캔하면 유니크 제약에 막힌다 | 수용 | 조정을 스캔 시작에도 실행, 중복 행 처리 |
| 과거 배치 Undo가 다른 파일을 옮긴다 | 수용 | 현재 코드에서 재현됨. `identity_mismatch` |
| 검사 후 폴더가 심볼릭 링크로 바뀌면 루트 밖으로 나간다 | 기각 | 같은 권한의 프로세스는 파일을 직접 바꿀 수 있어 이 설계의 위협 모델 밖이다. 파일 손실 경로도 아니다. 보장 범위에 명시 |
| 상대 심볼릭 링크가 이동 후 깨진다 | 수용 | 재현됨. 심볼릭 링크를 스캔·이동에서 제외. 측정 중 루트 밖 본문을 읽는 문제도 발견해 함께 해결 |
| `samefile`이 링크를 잘못 판정한다 | 수용 | `lstat`의 `st_ino`로 비교 |
| 충돌 재시도 목적지가 기록되지 않는다 | 수용 | 재시도 삭제 |
| `pending`인 파일을 재정리하는 경로 | 수용 | 조정을 정리 시작에도 실행 |
| 과거 배치 실패 사유가 화면에 안 나온다 | 수용 | 코드에서 확인. 모든 배치에 결과 카드 표시 |

Codex(2회차) 지적 판정이다. 반영 루프 상한(2회)에 도달해 이후 판단은 사람이 한다.

| 지적 | 판정 | 근거·조치 |
|---|---|---|
| 조정 실패를 무시하면 미해결 이동 위에 작업이 쌓인다 | 수용 | 미해결이 남으면 정리·되돌리기·스캔 거부 |
| 재스캔 행을 지우면 새 수동 분류를 잃는다 | 수용 | 행 삭제를 없앰. 미해결 중 스캔 차단으로 정상 경로에서 생기지 않음 |
| 이동 뒤 원자적 저장이 "이동 안 됨"으로 확정된다 | 부분 수용 | 정방향은 `unverified` 추가. 역방향은 재시도가 사유를 보고하므로 상태를 늘리지 않음 |
| Undo가 원위치 상위 폴더의 심볼릭 링크를 검사하지 않는다 | 수용 | `source_outside_root` |
| 스캔 후 교체된 원본에 다른 파일의 분류를 적용한다 | 수용 | 기존 `File.size`, `File.modified_at` 비교로 `skip` |
| 식별값에 `st_dev`가 없다 | 기각 | 같은 경로에 다른 볼륨이 마운트되고 inode까지 같아야 발생하며 결과도 덮어쓰기가 아니다. 반대로 `st_dev`는 외장 디스크를 다시 연결하면 바뀔 수 있어(이 환경에서 미측정) 정상 Undo를 막을 수 있다 |

구현 완료 후 Codex와 다른 세션의 리뷰어가 전체 변경을 따로 검토했다. 재현한 뒤 모두 실패 테스트부터 작성해 고쳤다.

| 지적 | 판정 | 조치 |
|---|---|---|
| 한글 경로의 NFC/NFD 차이로 제자리 파일을 번호 붙여 옮기고, 이력을 못 찾는다 | 수용 | macOS에서 경로를 NFC로 통일, 제자리 비교와 이력 조회에 반영 |
| `undo_pending`이 남아도 이력이 `undone`으로 표시된다 | 수용 | 상태 계산에 `undo_pending` 포함 |
| 기록 커밋 실패가 요청을 500으로 끝낸다 | 수용 | 기록 실패를 파일별 실패로 처리 |
| 배치 요약 저장 전 중단되면 이동 건수가 영구히 틀어진다 | 수용 | 이력의 건수와 되돌림 상태를 로그에서 계산 |
| 조정 때 권한 오류를 파일 없음으로 판단한다 | 수용 | 권한 오류는 미해결로 남김 |
| 조정 실패가 계속되면 스캔·정리·되돌리기가 잠기고 화면에 해제 수단이 없다 | 유지 | 2회차에서 수용한 설계. 사유를 화면에 표시하고 앱을 다시 시작하면 재시도한다. 드문 경우라 해제 UI는 만들지 않는다 |
